# Crypto XOR

## When to suspect this

- Ciphertext is hex/base64 and length is close to plaintext.
- Repeating patterns or known flag prefix likely.
- Source uses `^`, `xor`, `zip(key, data)`, repeating key.
- Challenge hints at one-time pad, stream cipher, keystream, reused key.
- `c1 xor c2` produces readable fragments.

## Fast triage checklist

- Decode hex/base64 first.
- Try single-byte XOR brute.
- Use known plaintext `flag{`, `CTF{`, JSON, PNG, ZIP.
- Check repeating key lengths.
- If multiple ciphertexts, XOR pairs.
- Score ASCII and crib drag.
- Recover key bytes position by position.

## Exploit skeleton

```python
#!/usr/bin/env python3
import string

ct = bytes.fromhex("HEX")
alphabet = bytes(string.printable, "ascii")

for k in range(256):
    pt = bytes(b ^ k for b in ct)
    score = sum(c in alphabet for c in pt)
    if score > len(pt) * 0.9:
        print(k, pt)
```

## Escalation path

- If single-byte fails, test repeating key.
- If two-time pad, crib drag against `c1 xor c2`.
- If stream cipher nonce reused, recover keystream from known plaintext.
- If key is generated by PRNG, recover seed/state.

## Common bypasses

- Data may be base64/hex encoded before XOR.
- Key may reset per line/block.
- Key may be index-based: `b ^ i`, `b ^ (i & 0xff)`.
- XOR may combine with rotate/add/sub/permutation.
- Plaintext may be compressed; look for magic after XOR.

## Rabbit holes

- Assuming high entropy means strong crypto.
- Trying AES tools on XOR.
- Ignoring known file magic.
- Not checking key alignment offset.

## Final solve checklist

- Encoding layer stripped.
- XOR type identified.
- Key/keystream recovery is documented.
- Plaintext or flag verifies.
